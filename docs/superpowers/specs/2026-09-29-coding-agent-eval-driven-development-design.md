# Coding Agent 评测驱动开发计划

## 目标

将当前最小 coding agent 演进为可量化优化的工程工具。首要目标是提升真实编码任务成功率，而非优先增加模型、RAG 或多代理复杂度。

## 范围与原则

- 保持标准库优先、workspace 隔离、模型适配层和单代理循环的现有边界。
- 先建立可复现评测与失败分类，再依据数据优化工具、提示词和循环。
- 每项能力以独立可验证单元交付；新增能力不得降低已有任务集成功率。
- 安全、预算、可恢复性是上线门槛，不以“模型会自行纠正”为前提。

## 成功指标

| 指标 | 定义 | 要求 |
| --- | --- | --- |
| 任务成功率 | 在干净 fixture 中完成验收命令的任务占比 | 每阶段提升；回归不得下降 |
| 首轮完成率 | 无人工干预完成的任务占比 | 单独记录 |
| 工具失败率 | 工具调用返回错误的比例 | 按错误类别持续下降 |
| 平均步骤数 | 成功任务的模型轮数 | 成功率不下降前提下优化 |
| 成本 | 单任务 token 与调用数 | 记录并设预算上限 |
| 安全事件 | 越界访问、不可恢复修改、预算失控 | 必须为零 |

## 阶段 A：建立真实性能基线

### 目标

建立 20–30 个可重复运行、自动验收的真实小型编码任务，使后续优化有明确因果依据。

### 任务集

按当前工具能力覆盖以下类型：

1. 定位并修复单文件逻辑缺陷。
2. 跨文件小改动与调用点同步。
3. 添加或修复单元测试。
4. 受限范围内的重构。
5. CLI 参数或错误提示修改。
6. 文件读取、精确编辑、命令执行失败后的自我纠正。
7. workspace 边界与危险命令拒绝。
8. 上下文压缩前后继续完成任务。

每个任务必须包含：隔离 fixture、任务说明、初始 Git 状态、验收命令、期望修改范围、最大步骤和 token 预算。

### 评测执行器

新增本地评测入口，针对每个任务：

1. 创建干净工作区副本。
2. 调用 agent 执行任务。
3. 运行任务验收命令。
4. 收集轨迹、工具调用、失败类型、步骤数、token 与最终 diff。
5. 输出 JSONL 明细及汇总报告。

结果按成功、验收失败、模型异常、工具异常、预算耗尽、步骤耗尽、安全拒绝分类。

### 基线验收

- 所有任务可在无真实 API 的确定性 MockProvider 下回放。
- 至少一套真实模型 profile 跑完整任务集。
- 每个失败都有任务 ID、失败阶段和原始证据。
- 基线报告成为后续变更的回归输入。

## 阶段 B：生产闭环加固

### B1：按失败数据优化决策和工具

仅处理阶段 A 中频率最高、影响成功率最大的失败类别：

- 补足工具 schema、描述和错误消息中的行动性信息。
- 对编辑失败回传精确可复制的上下文。
- 规范命令输出截断与关键信息保留。
- 对重复读取、重复测试和无效编辑增加可观测标记。

每次改动先增加对应回归用例，再跑完整评测集。

### B2：可恢复编辑

为 `edit_file` 建立 workspace 内的事务式 undo 记录：

- 修改前保存可恢复快照和操作元数据。
- 成功编辑后记录变更 ID、文件、前后内容摘要。
- 提供仅限当前 workspace 的 `undo` 工具。
- 撤销必须校验当前内容与预期版本，冲突时拒绝覆盖。
- 日志不得包含 workspace 外文件或环境密钥。

### B3：上下文与成本控制

- 对相同或高度相似的工具结果引用摘要，避免重复回灌大输出。
- 保留原始结果的本地 trace 指针，供诊断而非模型上下文使用。
- 记录每轮和每任务 token、工具次数、耗时；预算耗尽时明确返回可恢复状态。
- 压缩后继续校验 assistant/tool 配对完整性。

### B4：可观测性与交互

- 支持流式呈现模型文本与工具生命周期状态。
- 为每次运行写入结构化 trace：任务、轮次、请求摘要、工具调用、结果摘要、错误、预算、停止原因。
- 默认输出保持简洁；详细 trace 通过显式 flag 启用。

### B5：安全与隔离

- 将危险命令规则改为可测试的策略层，明确允许、拒绝、需确认三种结果。
- 继续解析真实路径并防止 symlink 越界。
- 对命令执行添加时间、输出和进程数边界。
- 所有安全拒绝均写入 trace，并返回模型可行动的原因。

### 阶段验收

- 完整评测集成功率不低于阶段 A 基线，并在目标失败类型上有可量化改善。
- undo、结果去重、压缩配对、安全策略均有单元与集成测试。
- trace 可重建一次任务失败的关键决策链。
- 所有测试、lint、typecheck（如项目定义）通过。

## 阶段 C：受控扩展

阶段 C 的前提是阶段 B 连续多次评测稳定，且单代理失败已证明由任务分解、代码审查或项目知识缺失导致。

### C1：角色化工作流

在同一运行时内引入可关闭的角色，而不是默认并行多代理：

- Planner：只读探索，输出小粒度计划与验收条件。
- Implementer：唯一具有写权限的执行角色。
- Reviewer：只读审查 diff、测试结果和风险。

角色通过结构化工件交接，禁止共享未压缩完整上下文。默认保留单代理 fallback。

### C2：项目记忆

引入按任务检索的、可审计的项目记忆：

- 仅索引用户允许的 workspace 文件与历史 trace 摘要。
- 检索结果必须附来源路径和时间，禁止无来源事实。
- 记忆写入以显式成功任务或人工确认的决策为主。
- 支持禁用、清除和每次注入内容的 trace。

不在单代理评测未稳定前接入向量数据库或长期自主记忆。

### C3：并行只读探索

仅对互不依赖的搜索、测试和审查并行执行：

- 一个任务中只允许一个写入者。
- 合并结果前校验 workspace 版本。
- 并行调度受总预算、超时和最大并发数限制。
- 并行收益必须通过任务耗时与成功率对照证明。

### 阶段验收

- 角色化模式相对单代理在目标任务类别上有显著成功率或耗时收益。
- fallback 可在角色、检索或并行组件失败时完成或安全退出。
- 记忆注入不泄露 workspace 边界外数据，且每条内容可追溯。
- 并行执行不存在写入竞争、预算失控或不可解释结果。

## 发布与回归流程

1. 新能力先补充单元测试和对应评测任务或失败回归。
2. 运行确定性 MockProvider 测试。
3. 运行完整评测集并与最近稳定基线比较。
4. 选择真实模型 profile 做固定样本验证，记录模型版本与配置。
5. 若成功率下降、出现安全事件或 trace 缺失，阻止发布。
6. 将报告、失败分类和下一轮最高优先级问题纳入版本记录。

## 不在当前路线内

- 未经评测证明的多代理自治。
- 提前引入 RAG、向量数据库或复杂长期记忆。
- 将安全隔离仅依赖于 prompt 或黑名单。
- 为抽象而抽象的大规模框架重写。
